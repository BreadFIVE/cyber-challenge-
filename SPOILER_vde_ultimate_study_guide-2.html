CIA Triad & Core Terminology

Week 1 — Foundations. These definitions come up in true/false and statement questions.

CIA Triad

  • Confidentiality — keeping data secret or private; controlling who can access information
  • Integrity — data is trustworthy and free from tampering; it must be authentic, accurate, and reliable
  • Availability — systems, networks, and applications must function as they should and when they should

The CIA triad is a common model that forms the basis for the development of security systems.

Integer Overflow & Underflow

Week 3 — Know the ranges, the wrap-around behaviour, and what happens in code.

Key Ranges (Exam-relevant only)

TypeSizeRange
char (signed)1 byte−128 to 127
unsigned char1 byte0 to 255

Note: short int, int, unsigned int, long int — marked "N/A for exam" on the slides.

Overflow — wraps to 0

unsigned char i = 255;
i = i + 1;  // i is now 0 — overflow!
// 255 = 11111111, + 1 = 100000000 (9 bits) → truncated to 00000000

When the result exceeds the maximum, it wraps around. A clock analogy: 23:59 + 1 minute = 00:00.

Underflow — wraps to max

unsigned char n = 0;
printf("n-1 = %hhu\n", n-1);  // prints 255

0 − 1 on an unsigned type wraps to the maximum value (255 for unsigned char).

Security Implication

If an overflowed integer value is used as a buffer size in malloc() or an array index, a dangerously small buffer is allocated. The caller then writes its expected large amount of data, causing a buffer overflow.

unsigned int size = user_value;  // attacker supplies huge value
size = size * 4;   // multiplication overflows → wraps to small value
char *buf = malloc(size);   // tiny buffer allocated
memcpy(buf, data, user_value * 4);  // OVERFLOW!
unsigned char x = 200; x = x + 100; What is x?
200 + 100 = ?
44. (200 + 100 = 300. 300 mod 256 = 44.)
An unsigned loop: for(unsigned int i=10; i>=0; i--) — what happens?
Think about what unsigned >= 0 means
Infinite loop. An unsigned int is always >= 0. When i reaches 0 and decrements, it wraps to UINT_MAX rather than going negative.
unsigned char x = 3; x = x * x * x * x * x ... — does the loop stop?
Mock exam Q8
Yes. x grows rapidly until x*x*x overflows, wrapping to a small value (possibly 0), which terminates the loop.
int x = INT_MAX; x = x + 1; Why is this an overflow?
Mock exam Q10 — the ACT of incrementing
x is incremented which causes the overflow. INT_MAX + 1 exceeds the signed int maximum. (x being set to INT_MAX is just the setup — the increment is the cause.)

Buffer Overflow

Weeks 4–5 — Know the mechanism, the payload structure, and the compiler flags.

How it works

  • C has no default bounds checking — writing past a buffer's end is silent
  • The buffer is at a lower address than the return address — overflow travels upward
  • Overflowing past the buffer hits: saved EBP → return address
  • When the function executes RET, the corrupted return address is loaded into EIP
  • The attacker now controls where execution goes next

Two Scenarios from the Slides

  • Scenario 1: Overwrite the return address with a crafted address → EIP redirected to attacker's code (shellcode)
  • Scenario 2: Overwrite other local variables on the stack → can trigger other vulnerabilities or cause unintended behaviour

Payload Structure — NOP Sled Exploit

(0x90 × N) + shellcode + [padding] + buffer_start_address

NOP sled ──────────────────────────────▶ shellcode ──▶ return addr overwrites
  • 0x90 = NOP (No Operation) — does nothing, EIP slides through
  • NOP sled — fills the buffer before shellcode, widening the target area
  • Return address — overwritten to point anywhere in the NOP sled
  • The payload must be larger than the buffer to overflow into the return address

Compiler Flags (Exam-listed)

FlagEffect
-fno-stack-protectorDisables stack canaries — intentionally vulnerable
-fstack-protector-allInserts canaries into ALL functions with local buffers
-z execstackMakes the stack executable (disables NX)
echo 0 | sudo tee /proc/sys/kernel/randomize_va_spaceDisables ASLR
A buffer is 32 bytes + 4 bytes EBP. How many bytes of padding to reach the return address?
32 + 4 = ?
36 bytes. Fill 32-byte buffer + overwrite 4-byte saved EBP = 36 bytes before reaching the return address slot.
char string[10]; — how many characters can it actually hold?
Don't forget the null byte
9 + the NULL byte. One byte is always reserved for the '\0' string terminator.
Why is the NOP sled larger the better?
Address precision
A larger NOP sled means a larger target window. The guessed return address only needs to land anywhere in the sled — not exactly on the shellcode.
Does a non-executable stack stop the return address being overwritten?
Slide quote
NO. "REM: It doesn't stop over-writing of the return address." — direct quote from the slides.

Unsafe C Functions & Safe Replacements

Weeks 4–5 — Every pair is exam-tested. Know both the vulnerability and the fix.

UnsafeWhy dangerousSafe replacement
gets(buf)No length limit whatsoever — reads until newline/EOFfgets(buf, sizeof(buf), stdin)
strcpy(dst, src)Copies until null byte with no length limitstrncpy(dst, src, sizeof(dst)-1)
strcat(dst, src)Appends with no check on remaining spacestrncat(dst, src, sizeof(dst)-strlen(dst)-1)

strncpy gotcha — always null terminate manually

char dest[10];
strncpy(dest, src, sizeof(dest) - 1);  // copies at most 9 bytes
dest[sizeof(dest) - 1] = '\0';          // MUST manually null-terminate!

If src fills all n bytes, strncpy does NOT add a null terminator. Subsequent string operations will overread.

The fgets heap overflow pattern — mock exam Q12

char *buffer = malloc(16);
char *target = malloc(16);
fgets(buffer, 100, stdin);   // ← tells fgets buffer is 100 bytes, but it's only 16!
// overflow spills into adjacent heap memory where target lives

Heap overflow fgets is given 100 as the limit but the buffer is only 16 bytes — adjacent heap chunks are corrupted.

Shellcode & NOP Sled

Week 5 — Know the definition, the NOP sled purpose, and the bypass techniques.

What is Shellcode?

  • A set of x86 machine instructions (not C code) injected into memory and executed by an exploited program
  • The term comes from its original purpose: spawning a root shell
  • Executed by the CPU directly — no compilation needed
  • EIP is set to the shellcode's address, so execution begins there
  • Size matters when delivered via buffer overflow — it must fit within the buffer

Mock Q27 "Shellcode is a sequence of hexadecimal numbers that represent operations to be interpreted in the context of the operating system."

Shellcode does NOT differ between stack and heap

Shellcode is machine code — it executes the same regardless of where it is stored in memory. Mock Q14 Answer: "It doesn't."

NOP Sled (0x90)

Memory: [NOP][NOP][NOP]...[NOP][SHELLCODE][padding...]
                    ↑
            EIP lands anywhere here and slides to shellcode
  • 0x90 = NOP instruction — does nothing, EIP advances by 1
  • Fills the buffer before the shellcode
  • If EIP is slightly wrong, it lands in the sled and slides to shellcode anyway
  • Larger sled = better chance of success

Mock Q19 "A NOP sled allows the return address from a function to move within a predefined memory address range, which makes the success of the exploit more probable."

Bypassing Non-Executable Stack (from slides)

  • ret2libc — take control of a stack frame to call a libc function (e.g. chmod, system). libc is always loaded in executable memory.
  • ret2data — place injected code in the data segment and jump to it
  • ret2code / ROP — use existing code snippets (gadgets) in the program to perform malicious actions
  • Patching — patch the executable or use runtime manipulation
ret2libc — True or False: it takes control of a complete stack frame?
Mock Q2
TRUE. ret2libc crafts a fake stack frame with the libc function address as the return address and the required arguments placed on the stack.
ret2data — True or False: places injected code in the data segment?
Mock Q3
TRUE. ret2data stores the payload in the .data segment and redirects the return address there — but W^X prevents this on modern systems.
Why must shellcode avoid null bytes (0x00)?
String functions
String functions like strcpy() and gets() treat 0x00 as the string terminator and stop copying — truncating the shellcode before delivery.

Format Specifiers & Format String Vulnerabilities

Week 6 — Know all 7 specifiers, both vulnerability types, and why printf(user_input) is dangerous.

Format Specifiers — All 7 for the exam

SpecifierPrintsSecurity relevance
%cSingle characterCan read char values off stack
%dSigned decimal integerReads stack values as signed ints
%uUnsigned decimal integerReads stack values as unsigned ints
%xUnsigned hex (lowercase)⚠️ Classic stack leak — reads addresses as hex
%sNull-terminated string⚠️ Reads string from arbitrary stack address
%pPointer / memory address (hex)⚠️ Leaks memory addresses — defeats ASLR
%nNothing printed — writes byte count to address☠️ Enables arbitrary memory writes

Note: fprintf is explicitly listed as NOT on the exam. Only printf and sprintf.

Why printf() is variadic — and why that's dangerous

Format functions accept 0 or more arguments. Arguments are placed on the stack. The format string decides how many to read at runtime — it doesn't check. If there are more format specifiers than arguments, it reads whatever is on the stack next.

printf("%s %d %d", str, i);   // 3 specifiers, 2 args → reads garbage from stack!
printf(user_input);            // ← VULNERABLE: user controls specifiers

Static vs Dynamic Format String Vulnerability

TypeHow it occursWhat the attacker can do
StaticFixed format string but more specifiers than arguments (e.g. extra %d)Read stack values — info disclosure
DynamicUser input used directly as the format string: printf(user_input)Read stack (%x, %p), write memory (%n), crash (%s with bad addr)

Mock Exam Q11 — the most commonly missed question

char input[128];
fgets(input, sizeof(input), stdin);
printf(input);    // ← THE VULNERABILITY IS HERE

Common wrong answer: "The input buffer can be overflowed" — NO, fgets limits input correctly.

Correct answer: "A user-controlled input string is passed directly as the format string to printf." — This is a format string vulnerability, not a buffer overflow.

What does %n do and why is it so dangerous?
It writes, not reads
%n writes the number of bytes printed so far to the address provided as the argument. Attacker controls the address and value — arbitrary memory write.
printf("%x %x %x") with no arguments — what happens?
Stack reading
printf reads three values from the stack (wherever arguments should be) and prints them as hex. Leaks stack contents including addresses and sensitive values.
What is the safe way to print user input with printf?
Always a fixed format string
printf("%s", user_input); — always use a fixed format string with user data as the argument, never as the format string itself.

Heap & Heap Overflow

Week 7 — Know the three memory regions, the four functions, and what heap overflow does.

Three Memory Regions

RegionWhat's storedLifespan
.data / .bssGlobal variables (.data = initialised, .bss = uninitialised)Entire program
StackLocal variables, return addresses, function parametersDuration of function call
HeapDynamic memory (malloc/calloc)Until free() is called

Heap Functions — the four from the slides

FunctionWhat it doesKey difference
malloc(n)Allocates n bytes on heapDoes NOT initialise memory
calloc(n, size)Allocates n×size bytes on heapInitialises ALL bytes to zero
realloc(ptr, newSize)Resizes existing allocationMay return a new pointer
free(ptr)Returns memory to systemDoes NOT zero the memory

malloc returns NULL on failure — always check before use. If free() is never called = memory leak.

Heap Overflow

Just like a stack buffer overflow but on the heap. Writing past the end of a heap buffer corrupts adjacent heap chunks.

char *buf1 = malloc(10);
char *buf2 = malloc(10);
strcpy(buf1, "AAAAAAAAAAAAAAAAAAA");  // overflows into buf2!

buf1 and buf2 are adjacent on the heap. Overflowing buf1 writes into buf2's data — or into heap chunk metadata.

Memory Leak

If malloc'd memory is never freed, it is never returned to the allocator. Available heap memory shrinks over time. The slides call this a "Memory Leak" — situations where there are objects on the heap no longer used.

Fuzzing Lifecycle (6 steps)

  1. Identify the target
  2. Identify inputs — file, stdin, network, etc.
  3. Generate fuzzed data — using one of the methods below
  4. Execute fuzzed data — run the target with the input
  5. Monitor for exceptions — log crashes, hangs
  6. Determine exploitability — is EIP controlled? Is this a real vulnerability?

Three Fuzzing Methods

MethodHow it worksKey limitation
Mutation-basedTake valid inputs and apply random changes (bit flip, byte flip, arithmetic, insert/delete). Tools: zzuf, radamsa.Limited coverage; high false positive rate; may miss semantic bugs
Generation-basedCreate inputs from scratch using a format specification/grammar.High computational overhead; requires writing a spec; limited variability
Evolutionary-basedUses genetic algorithms + feedback from the target (code coverage) to evolve inputs. Tool: AFL.High computational overhead; potential for stagnation in local optima

zzuf — mutation-based tool

zzuf -r 0.01 -s 1000 < input.txt
# -r = ratio of bits to flip, -s = seed

One of the most common bit-flipping fuzzers. Corrupts user-contributed data by randomly flipping bits. Output is reproducible based on parameters.

eog — the fuzzing lab target

eog = Eye of GNOME — a Linux image viewer. Used in the lab as the fuzzing target. Malformed image files are fed to it using zzuf and crashes are observed.

File Header Mutation — Mock Q28

Key point: Mutation should be carefully applied to file headers to ensure the file will still be opened by the program under test.

If magic bytes or headers are corrupted too aggressively, the program rejects the file immediately — the interesting code is never reached and the fuzzer wastes cycles.

AFL & Code Coverage

Week 9 — AFL is the state of the art. Know exactly what it does and its limitations.

AFL — American Fuzzy Lop

  • Uses compile-time instrumentation and genetic algorithms
  • Discovers test cases that trigger new internal states in the target
  • Substantially improves code coverage compared to other fuzzers

AFL's 3 Key Strategies:

  1. Input Generation — generates initial seed inputs
  2. Mutation-based fuzzing — flips bits, inserts/deletes bytes, other transformations
  3. Feedback-Driven Optimisation — identifies inputs triggering unique behaviour → used as seeds for further mutation
  4. Genetic Algorithms (seed selection) — ranks test cases by effectiveness, mutates the best ones
  5. Corpus Management — maintains a corpus of interesting cases (crashes/hangs) to guide the fuzzer

AFL Limitations — all 5 from the slides

  • Logs crashes only — won't find logic errors or info leaks
  • Stdin / file input only — can't natively fuzz network programs
  • Linux only
  • Need to build target from source using AFL tools
  • No native parallelisation

Code Coverage

  • Definition: a metric determining the number of lines of code successfully validated under a test procedure
  • Good coverage: generally >80%

Coverage Criteria (from slides):

  • Condition — all boolean expressions evaluated for true and false
  • Decision — all if-elseif-else statements covered
  • Loop — every loop tested: zero times, once, many times
  • Entry and Exit — all possible calls and return values tested
  • Parameter Value — all possible values for parameters tested
What makes AFL different from simple mutation fuzzing?
Feedback + genetic algorithms
AFL uses compile-time instrumentation to track code coverage. Inputs that trigger new code paths are kept as seeds for further mutation — feedback-driven evolution.
AFL finds a crash. What is the LAST step of the fuzzing lifecycle?
Mock Q final step
Determine exploitability — assess whether the crash is a real security vulnerability that could be leveraged (e.g. is EIP controlled?).

Memory Protections

Week 10 — The four protections: NX stack, W^X, Stack Canaries, ASLR. Know what each stops and what bypasses it.

1. Non-Executable Stack (NX bit)

  • Marks the stack as non-executable via the OS
  • Prevents: execution of NOP sleds and shellcode on the stack
  • Does NOT prevent: overwriting the return address — "REM: It doesn't stop over-writing of the return address." (direct slide quote)
  • Bypasses: ret2libc, ret2data, ret2code, ROP, patching
  • Implemented via the NX bit (No eXecute) in x86 processors

2. W^X (Write XOR Execute)

  • A security policy: memory is either writable OR executable — never both
  • Writable memory (e.g. heap, stack) = non-executable
  • Executable memory (e.g. .code) = non-writable
  • Makes it impossible to inject payloads anywhere
  • On 64-bit architectures: always enabled, cannot be disabled
  • On 32-bit: can be globally disabled or selectively enabled/disabled
  • Still vulnerable to: ret2code, ROP, ret2libc, patching — you can still control the return address

3. Stack Canaries

  • 32-bit values placed between buffers and sensitive data (return address) at compile time
  • On buffer overflow, the canary is overwritten before the return address is reached
  • Application detects the change on function return → outputs "*** stack-smashing detected ***"

Ideal stack layout (with -fstack-protector):

Var 1 | Var 2 | Var 3 | char buffer[32] | Canary | EBP | Return address | Parameters

Buffers are placed at the END of the frame (lowest addresses) — any overflow immediately hits the canary.

Three Canary Types:

  • Null canary — all zeros (0x00000000)
  • Terminator canary — 0x000aff0d: 0x00 stops strcpy, 0x0a/0x0d stop gets, 0xff stops some functions
  • Random canary — randomly generated, normally starts with 0x00

4. ASLR — Address Space Layout Randomisation

  • Randomises the location of the stack, heap, libraries, and executable every time a process loads
  • Makes it difficult to know where to redirect EIP — the address of shellcode or libc changes each run
  • Disable on Linux: echo 0 | sudo tee /proc/sys/kernel/randomize_va_space

ASLR Weaknesses (from slides):

  • Relies on entropy — most 32-bit and constrained systems have limited entropy
  • Memory leaks can bypass or predict outcomes
  • Third-party libraries or older software may not be compiled with ASLR support
  • Bare-metal systems don't necessarily have an OS
